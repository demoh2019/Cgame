# Перенос issues и pull requests Godot

Источник: [`godotengine/godot`](https://github.com/godotengine/godot). Получатель: [`demoh2019/godot`](https://github.com/demoh2019/godot).

**Это инструмент миграции с контрольными точками, а не утверждение, что 123 тысячи объектов уже перенесены.** GitHub не поддерживает прямой перенос чужих PR с авторством, отзывами и историей. Он не позволяет переносить чужие issues без доступа к исходному репозиторию. Сценарий аккуратно хранит ссылки на оригиналы и не делает merge в `master`.

## Режимы

- `archive`: сохраняет **метаданные всех** issues и PR, по 100 записей на страницу (включая закрытые и слитые). Файлы `misc/upstream_archive/page-xxxxx.json.gz` — оригинальные ответы GitHub REST `/issues`. **Комментарии, review threads, полноценные diffs и бинарные вложения в архив не входят**; ссылки на оригиналы сохраняются. Контрольная точка в `.github/upstream_mirror_state.json`.
- `issues`: создаёт GitHub Issues из upstream issues; сохраняет автора в теле, исходный статус, метки текстом и ссылку. Закрытые источники создаются и затем закрываются. Номера и авторы в GitHub не сохраняются. Запрещено создавать новые issues, если функция Issues отключена.
- `pr-records`: создаёт **issues-трекеры**, связанные с оригинальными upstream PR. Это **не** GitHub PR с кодом, и режим не заявляет обратного.
- `prs`: переносит **только открытые, не draft PR, нацеленные на `master`**, в отдельные ветки `upstream-pr-N` как **draft PR**. Патч вычисляется по `upstream BASE...HEAD` и накладывается на HEAD форка. Конфликтующие, пустые и несовместимые PR пропускаются; никаких автоматических merge не производится. Переносимые PR требуют обязательной проверки человеком и тестов. Работа с другими base branch не поддерживается.

**Внимание:** создание десятков тысяч issues или тысяч PR может сделать репозиторий неудобным, вызвать лимиты API и задействовать GitHub Actions. Рекомендуется начать с `archive` и небольших тестовых партий. Массовая миграция исходных PR — это перенос непроверенного чужого кода; его нельзя автоматически вливать в основную ветку.

## Как запустить

1. **Перед `issues` и `pr-records`:** включите GitHub **Settings → General → Features → Issues** в своём форке (на момент подготовки инструмента Issues отключены).
2. Просмотрите и примите PR, добавляющий `.github/workflows/upstream_mirror.yml`. **До merge на ветку по умолчанию workflow может не показываться в меню Actions.**
3. Откройте GitHub **Actions → Mirror Godot upstream issues and pull requests → Run workflow**. Сначала оставьте `apply_changes=false` (dry-run).
4. Выберите нужный режим и повторяйте запуск с `apply_changes=true`; курсоры хранятся в `.github/upstream_mirror_state.json`, поэтому следующий запуск продолжит с прошлой позиции. Для архива выбирайте `pages=20` (до 2000 записей за запуск), для issues — `limit=20`, для открытых PR — `limit=2` или меньше.
5. Проверяйте журнал Actions, количество PR/Issues и локальные тесты/CI перед дальнейшим переносом. Workflow **не запускается автоматически по расписанию**.

### Локальная работа

```bash
python3 -m unittest discover -s misc/scripts/upstream_mirror_tests -v
python3 misc/scripts/upstream_mirror.py archive --pages 20 --dry-run
python3 misc/scripts/upstream_mirror.py archive --pages 20
GITHUB_TOKEN=... python3 misc/scripts/upstream_mirror.py issues --limit 10 --dry-run
GITHUB_TOKEN=... python3 misc/scripts/upstream_mirror.py issues --limit 10
GITHUB_TOKEN=... python3 misc/scripts/upstream_mirror.py pr-records --limit 10
GITHUB_TOKEN=... python3 misc/scripts/upstream_mirror.py prs --limit 2
```

`prs` требует локального `git`, подключения `origin` с разрешением на push и достаточного объёма диска. Используйте токен минимально необходимых прав `contents`, `pull_requests` и `issues`. **Не публикуйте токен и не запускайте недоверенный код из PR**. Во время CI используются `GITHUB_TOKEN` и права текущего workflow.

## Ограничения и сверка

- Снимки в `archive` сохраняют JSON метаданных постранично; для полного переноса комментариев, review и вложений понадобится отдельный экспорт и хранение.
- `issues` и `pr-records` — обычные GitHub issues с маркером `<!-- upstream-mirror:OWNER/REPO#NUMBER -->`; он нужен для поиска дубликатов. Есть повторная проверка недавних целевых issues, если создание произошло до сохранения state.
- Состояние сохраняется локально после каждого объекта и коммитится workflow в конце партии. При неполном запуске или неверной конфигурации веток может потребоваться сверка вручную.
- Изменение исходного текста после импорта **не синхронизируется**; этот инструмент переносит объекты один раз, а не держит их live-репликами.
- При переносе PR не выполняются сборка, тесты Godot, статусные проверки, ревью или автоматическое разрешение конфликтов. Проверяйте изменения перед merge.
- GitHub API может ограничивать частоту запросов. Скрипт повторяет запросы при 429, 5xx и явных rate-limit ошибках, но иногда следует уменьшить размер партии.
- Чтобы остановить работу, не запускайте новые партии; миграция **не** выполняется фоново.
